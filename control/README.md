# control — Steward control plane

A single Phoenix application with Ash 3. Specification: `docs/10-components/07-control-plane-and-review-queue.md` (read §4 and §5.0 first), `docs/10-components/06-policy-engine.md`, `docs/20-contracts/12-data-model-and-schemas.md`, conventions in `docs/40-engineering/18-engineering-conventions.md` §2.

## Layout

Four top-level namespaces, each a `boundary` (doc 07 §4):

```
control/
  lib/
    steward/
      core.ex, core/            Steward.Core: the Ash domains (Targets, Branches, Policies,
                                 Reviews, Audit — nested as Steward.Core.* because the
                                 `boundary` library's nested-boundary mechanism requires a
                                 sub-boundary's module name to be prefixed by its parent's),
                                 their resources, actions, state machines, and the Repo.
      coordinator.ex             Steward.Coordinator: Branch GenServers, Spark lifecycle DSL,
                                 Reactors (not yet built — E2-E4).
      jobs.ex                    Steward.Jobs: AshOban triggers and workers (not yet built — E8).
    steward_web/                 Phoenix controllers for /v1 (doc 10), gRPC services, LiveView
                                 (not yet built — E9, E10).
  config/
  test/                          ExUnit; test/schema/ for the cross-cutting schema tests
  priv/repo/migrations/          Generated by `mix ash.codegen`; committed, never hand-written
  mix.exs
```

Dependency direction, enforced at compile time by `boundary`:

```
StewardWeb ──▶ Steward.Coordinator ──▶ Steward.Core
Steward.Jobs ──▶ Steward.Core (and Coordinator for repairs)
```

`Steward.Core` must not reference a GenServer, the data-plane client, or anything in `StewardWeb`; that is what guarantees doc 13 invariant 10 (no remote call inside a transaction).

Local database: `tools/stack/stack up` starts `control-db` on port 5433 (database `steward_control`); see `tools/README.md`. (This machine runs a local Postgres.app instance on the same port in place of the Docker-based stack — same credentials shape, `postgres`/`postgres`.)

## Rules that matter most here

- Actions are the only write path; no `Ecto.Changeset` or `Repo.insert` in application code (doc 18 §2).
- Every action has a policy; `Steward.PolicyCoverageTest` fails the build otherwise (doc 07 §10).
- Migrations are generated with `mix ash.codegen` and committed; they must match the DDL in doc 12. Never hand-write a migration — CHECK constraints, partial unique indexes, native triggers, and the append-only grants are all declared on the resources themselves (`check_constraints`, `identities ... where:`, `custom_statements`) and flow into the generated migration. Apply with `mix ash.migrate`.
- The `events` row is appended inside the same transaction as the state change, via `Steward.Core.Audit.AppendEvent` (an `after_action` hook), never a notifier (doc 07 §5.0).
- Reactor steps before the checkpoint compensate; steps after it are heartbeat-repaired (doc 07 §5.0, doc 13) — the Reactors themselves are E2-E4, not yet built.

## Commands

```sh
mix deps.get
mix ash.codegen <name>     # after changing a resource; review, then commit the migration
mix ash.migrate            # apply pending migrations
mix ash.codegen --check    # drift check (MigrationDriftTest runs this)
mix test
mix format
mix steward.contracts.gen          # regenerate lib/steward_plane/ from contracts/proto
mix steward.contracts.gen --check  # fail if the checked-in stubs are stale
```

`steward.contracts.gen` needs `python3 -m grpc_tools.protoc` (`pip install grpcio-tools`; set `STEWARD_PYTHON` to pick the interpreter) and `protoc-gen-elixir` (`mix escript.install hex protobuf`).

## Branch coordinator

`Steward.Coordinator` (E2) runs one process per non-terminal branch, found through `Steward.Coordinator.Registry` and supervised by a `PartitionSupervisor`; process state is a cache of the row. Transitions go through `Steward.Coordinator.Branch.transition/5` (an Ash action guarded by `lock_version`); heartbeats through `Steward.Coordinator.Heartbeat.handle/2`, decided by the declared matrix in `Steward.Coordinator.HeartbeatMatrix`. Tests that start processes use `Steward.CoordinatorCase`; `boot_sweep` is off in `config/test.exs`.

## Lifecycle flows

`Steward.Coordinator.Flows` (E4) is how a controller or a job drives a branch: `create_branch/1`, `propose/1` (answers with the computing changeset, finishes in the background), `withdraw/1`, `abandon/1`. Each is one Reactor under `Steward.Coordinator.Reactors` with a single checkpoint; steps after it use `Reactors.BestEffort` and cannot fail the flow. Tests that run flows end to end use `Steward.SessionHarness` (the shared Session listener plus a connected fake data plane). Scheduled work is Oban: AshOban triggers on the resources, plain cron workers in `Steward.Jobs`; drain triggers in tests with `AshOban.Test`.

## Session host

`StewardWeb.Plane.Server` serves `steward.plane.v1.Session` on port 50051 (E3). It is framing and identity only; `Steward.Coordinator.Plane` holds the per-data-plane sessions and the instruction queue (`Plane.send_instruction/4`: reply deadlines, re-send on reconnect), and `Plane.Upstream` handles what data planes send. Development trusts the `x-steward-data-plane-id` header; `config/runtime.exs` requires `PLANE_TLS_CERTFILE`, `PLANE_TLS_KEYFILE` and `PLANE_TLS_CACERTFILE` in production, and identifies a data plane by its client certificate. Tests start their own listener on a free port; the fake data plane dials it (`transport: {:grpc, address}`).

## Fake data plane (test support)

`test/support/fake_data_plane.ex` (`Steward.FakeDataPlane`, E13) stands in for a customer's data plane so the control plane never waits on Rust. It speaks the generated `steward.plane.v1` messages, either in-process (`transport: :direct`, for coordinator and reactor tests) or over a real `Session.Connect` stream (`transport: {:grpc, address}`, for E3). Failures are scripted per instruction kind; the moduledoc maps each behaviour to the doc 13 §6 row it reproduces, and `test/fake_data_plane/failure_rows_test.exs` has one scenario per row. `Steward.FakeDataPlane.Matrix` is the data plane's half of the doc 13 §6.8 reconciliation table.
